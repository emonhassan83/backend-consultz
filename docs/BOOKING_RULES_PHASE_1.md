# Booking Rules Phase 1

## Purpose

Phase 1 adds the foundation for expert-specific booking rules without changing the current booking flow. Existing fixed `BookingSlots` remain active for now, but the new rules and helper utilities prepare the backend for dynamic slot generation in Phase 2+.

## Why fixed DB slots are being deprecated

The old slot model stores pre-generated availability blocks. That works for simple hourly bookings, but it does not fit the optimized packing mode needed for 15, 30, and 60 minute sessions with different buffer times.

Dynamic calculation will let the backend:

- consume only the exact booked duration plus post-session buffer;
- avoid blocking a whole hour for a short session;
- calculate available starts based on the requested session duration;
- apply expert-specific notice, horizon, and buffer rules consistently;
- reduce dead gaps between bookings.

## Expert bookingRules schema

`bookingRules` is stored on the expert user profile.

```ts
bookingRules: {
  minNotice: number
  bookingHorizonDays: number
  slotBufferStep: number
  bufferRules: Array<{
    duration: number
    buffer: number
  }>
}
```

Units are fixed:

- `minNotice` is always hours.
- `bookingHorizonDays` is always days.
- `slotBufferStep` is always minutes.
- `bufferRules[].duration` and `bufferRules[].buffer` are always minutes.
- `bufferRules` is generated by the backend from `slotBufferStep`.

Client update payload should send only the rule inputs:

```json
{
  "bookingRules": {
    "minNotice": 2,
    "bookingHorizonDays": 60,
    "slotBufferStep": 3
  }
}
```

## Default values

If an expert has no custom rules, the backend uses:

```ts
{
  minNotice: 2,
  bookingHorizonDays: 60,
  slotBufferStep: 5,
  bufferRules: [
    { duration: 15, buffer: 5 },
    { duration: 30, buffer: 10 },
    { duration: 60, buffer: 20 }
  ]
}
```

Validation rules:

- `minNotice` must be `0` or greater.
- `bookingHorizonDays` must be at least `1`.
- `slotBufferStep` must be a whole number and cannot be negative.
- `bufferRules` is an array of `{ duration, buffer }`.
- `duration` must be a positive number.
- `buffer` must be `0` or greater.

## Buffer selection by session duration

Buffer is post-session only.

The helper checks `bufferRules` using an exact duration match:

- 15 minute session -> 5 minute buffer by default.
- 30 minute session -> 10 minute buffer by default.
- 60 minute session -> 20 minute buffer by default.

The default calculation is:

```ts
buffer = slotBufferStep * (duration / 15)
```

Example with `slotBufferStep: 3`:

```ts
[
  { duration: 15, buffer: 3 },
  { duration: 30, buffer: 6 },
  { duration: 60, buffer: 12 }
]
```

If no buffer rule exists for the requested duration, the helper throws a clear error instead of guessing. This is intentional so bad configuration is caught early.

## Shared helper utilities

The shared helper lives at:

```text
src/app/modules/booking/bookingRules.utils.ts
```

It exports:

```ts
getDefaultBookingRules()
resolveBookingRules(expert)
getBufferForDuration(rules, duration)
parseLocalDateTimeToUtc(date, time, timezone)
buildBookingInterval({ date, startTime, duration, timezone, rules })
isWithinBookingHorizon(startAt, rules)
isMinNoticeSatisfied(startAt, rules)
```

## UTC and local time calculation

The client sends local date/time with timezone, for example:

```ts
{
  date: '2026-07-30',
  startTime: '10:00',
  duration: 30,
  timezone: 'Asia/Dhaka'
}
```

`buildBookingInterval` converts that local session into UTC-backed date fields:

```ts
{
  date,
  startAt,
  endAt,
  bufferEndAt,
  startTime,
  endTime,
  bufferTime,
  localDate,
  localStartTime,
  localEndTime,
  timezone
}
```

Where:

- `startAt`, `endAt`, and `bufferEndAt` are UTC `Date` values.
- `startTime` and `endTime` are UTC `HH:mm` strings.
- `localDate`, `localStartTime`, and `localEndTime` preserve the requested timezone view.
- `bufferEndAt` is calculated as `local start + duration + selected buffer`.

## What Phase 1 does not change

Phase 1 intentionally does not change runtime booking behavior.

- No dynamic slot API yet.
- No booking create request change yet.
- No booking payment changes.
- No job scheduler changes.
- No cancellation/refund logic changes.
- Old `BookingSlots` are still active.
- Existing booking, payment, notification, and job flows should behave the same.

## Next phase dependencies

Phase 2+ can use this foundation to:

- add `GET /booking-slots/dynamic`;
- calculate slots from expert availability, existing bookings, requested duration, and buffer rules;
- migrate booking create from old `slot` to `date`, `startTime`, `sessionDuration`, and `timezone`;
- store UTC and local booking interval fields on the booking record;
- update jobs to use `startAt`, `endAt`, and `bufferEndAt`;
- eventually deprecate fixed `BookingSlots` after the dynamic flow is fully stable.
